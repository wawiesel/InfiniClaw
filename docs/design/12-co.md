# 12 — Chain of Command

## Rank Structure

| Title | Who | Scope |
|-------|-----|-------|
| **CO** (Commanding Officers) | Captain + Operator | Fleet-wide authority |
| **XO** (Executive Officer) | Chief Navigator (highest-rank navigator on bridge) | Fleet coordination, second in command |
| **Chief** | Highest-rank active bot per duty room | Room lead — triage, delegation, review |

"Highest rank" = lowest rank number (rank 1 outranks rank 2).

## Chain of Command

```
Captain → Operator → Chief (per room) → other bots
```

The Captain sets direction. The Operator executes fleet management and relays orders. Each duty room's Chief leads the bots in that room — triaging messages, delegating work, and reviewing output.

The Chief Navigator is special: they serve as **XO**, coordinating across the fleet from the bridge. All other Chiefs are scoped to their duty room (Chief Engineer in Engineering, Chief Architect in Astrometrics).

## The Chief Role

Each duty room has a **Chief** — the lowest-rank-number active bot in that room. The Chief acts as the primary orchestrator, triage agent, and reviewer for the room.

### The Manager Role

In the **Branch and Merge** architecture, the Chief's Main Brain acts as a manager:
1.  **Fielding:** It responds instantly (within 2 seconds) to unaddressed messages on the main timeline.
2.  **Branching:** If a request requires significant work, the Chief uses the `branch_to_thread` tool to create a task-specific Branch Brain.
3.  **Delegation:** In the thread, the Chief pings other bots (e.g., `@Cid`) to perform the work.
4.  **Reviewing:** The Chief's Branch Brain interacts with the non-Chief bot in the thread, reviewing findings and approving code changes.
5.  **Merging:** Once approved, the Chief merges the task outcome into `MEMORY.md` and posts a final summary to the Captain on the main timeline.

## Chief Election

Chief is determined from `fleet.json` at startup and updated at runtime via relay lifecycle messages.

### Startup
Each bot reads the `IsChief` environment variable (injected by the host based on `fleet.json`) to set its initial badge. Display name badges: ⭐ = Chief, 🟢 = active.

### Runtime Updates
When the relay dismisses or joins a bot, it posts a lifecycle message via intercom (e.g., `HERACLES: Cid stopped`). All bots parse these messages to update their in-memory `roomRoster` and re-evaluate who holds the Chief role.

> **Status:** Implemented. Relay broadcasts lifecycle messages after dismiss, sleep, report, and promote/demote via the bot's duty room intercom connection. Bots update `roomRoster` and re-evaluate Chief on receipt.

## Work Breakdown Structure (WBS)

Each duty room has a **WBS** — a deliverable-oriented hierarchical decomposition of all work in scope. The Chief is the sole writer; crew bots observe their assignments and execute work.

### Principles

- **100% Rule**: The WBS captures all work in scope. Every child sums to its parent.
- **Mutually Exclusive**: No work item appears under two parents.
- **Outcome-Oriented**: Items describe deliverables, not activities.
- **Rolling Wave**: Near-term work is decomposed in detail; future work stays at higher levels.

### Hierarchy

```
Phase (Level 1)
  Deliverable (Level 2)
    Work Package (Level 3)
      Task (Level 4 — assignable unit)
```

Only tasks (leaf nodes) are assigned to bots. Higher levels aggregate progress from their children.

### Storage

- **S3**: Source of truth — `wbs/{room}.json` in the S3 bucket. Atomic read/write via the relay's S3 client.
- **Secrets repo**: JSON disk echo at `bots/wbs/{room}.json` and `bots/wbs/todos/{bot}.json`. Downstream artifact, git-tracked. Relay writes after every S3 update.
- **No local-only files**: The relay never reads WBS from disk. S3 is always authoritative.

### Item Schema

```
{
  "id": "1.2.3",                    // hierarchical WBS code
  "parent": "1.2",                  // parent WBS ID (null for root)
  "title": "Fix credential proxy",
  "description": "...",
  "type": "task",                   // phase | deliverable | work_package | task | milestone
  "status": "assigned",             // pending | ready | assigned | in_progress | review | done | blocked | cancelled
  "priority": "high",               // critical | high | medium | low
  "assignee": "cid",                // bot name, or null
  "source": "issue#37",             // GitHub issue, PR, or Captain directive

  "dependencies": [
    {"predecessor": "1.2.1", "type": "FS", "lag": 0}
  ],

  "estimates": {
    "optimistic": 1,                // hours
    "likely": 3,
    "pessimistic": 8,
    "expected": 3.5,                // (O + 4M + P) / 6
    "stddev": 1.17                  // (P - O) / 6
  },

  "actual": {
    "started_at": "2026-03-15T06:00:00Z",
    "completed_at": null,
    "effort_hours": null
  },

  "schedule": {
    "earliest_start": "2026-03-15T06:00:00Z",
    "earliest_finish": "2026-03-15T09:30:00Z",
    "latest_start": "2026-03-15T08:00:00Z",
    "latest_finish": "2026-03-15T11:30:00Z",
    "total_float": 2.0,
    "is_critical": false
  },

  "acceptance_criteria": ["Build passes", "Tests added", "PR merged"],
  "due_date": null,
  "created_at": "2026-03-15T05:00:00Z",
  "updated_at": "2026-03-15T06:00:00Z"
}
```

### Access Model

| Role | Read | Write |
|------|------|-------|
| **Chief** | Full WBS | Full CRUD — add, update, assign, remove, reorder. Completion requires verification. |
| **Crew bots** | Assigned items only | None — observe and execute, report results in room |
| **Captain/Operator** | Full WBS | Override — priority, scope, assignments, due dates, completion |

Bots interact with the WBS through InfiniClaw MCP tools. The Chief has write-capable tools; crew bots have read-only tools.

### Completion Verification

The Chief and Operator are responsible for verifying that todos a bot claims are completed actually meet acceptance criteria before the corresponding WBS item is marked done. Bots cannot self-verify their own work — the Chief or Operator must confirm.

### WBS is Universal

WBS is the single source of truth for all work, regardless of tracking system. Some WBS items naturally map to GitHub PRs, issues, or other artifacts, but the WBS is the authoritative record. GitHub issues are inputs to the WBS (via `source` field), not a parallel tracking system.

### Estimation (PERT)

Every task gets a three-point estimate before assignment:

- **O** = Optimistic (best case)
- **M** = Most Likely (normal conditions)
- **P** = Pessimistic (worst case)

```
Expected = (O + 4M + P) / 6
Std Dev  = (P - O) / 6
```

Bot tasks have high variance. Set the O/P spread wider than for human workers.

### Dependencies

Two supported relationship types:

| Type | Meaning | Use |
|------|---------|-----|
| **FS** (Finish-to-Start) | B can't start until A finishes | Most common |
| **SS** (Start-to-Start) | B can start once A starts | Parallel work |

### Critical Path

The critical path is the longest chain of dependent tasks — it determines minimum project duration.

1. **Forward pass**: Compute earliest start/finish for each task
2. **Backward pass**: Compute latest start/finish from the end
3. **Float** = Latest Start - Earliest Start
4. Tasks with **zero float** are on the critical path

The Chief assigns critical-path tasks first, to the most capable available bot.

### Data Flow

```
WBS (S3, rich structure)
  → Chief triages, sequences by priority and dependencies
  → Chief produces prioritized global todo list for the room
  → Chief distributes todo items to self and onduty crew bots
  → Bots execute assigned work
  → Bots post results in the room
  → Chief reviews output
  → Chief marks WBS item done
  → Relay unblocks dependents in S3
  → Disk echo updated in secrets repo
```

### Chief Responsibilities

1. **Consult WBS** — On startup and after every idle period, read the WBS to determine current state.
2. **Decompose** — Break deliverables into estimable tasks following the 100% rule.
3. **Estimate** — PERT three-point estimate for every task before assignment.
4. **Schedule** — Compute critical path, set dependencies, determine assignment order.
5. **Linearize** — Produce a prioritized, linear TODO list from the WBS for the room.
6. **Distribute** — Push TODO items to onduty bots via the standard todo system. Critical-path tasks first. WIP limit: 1 per bot.
7. **Review** — When a bot posts results, verify against acceptance criteria.
8. **Complete** — Mark WBS items done only after Chief or Operator has verified the work. Relay unblocks dependents automatically.
9. **Rebalance** — If a bot is stuck or dismissed, reabsorb its items and reassign.
10. **Report** — Track EVM metrics and velocity. Surface schedule risk to Captain.

### Single-Bot Case

If only one bot is onduty, that bot is automatically the Chief. It self-assigns from the WBS and executes. No delegation overhead. When a second bot reports, the lower-rank-number bot becomes Chief and redistributes work.

### Relay Integration

The relay manages WBS mechanically:

- **On `!report`**: Read WBS from S3, inject assigned todo items as initial context for the bot.
- **On `!dismiss`**: Reabsorb all assigned items (`assignee: null, status: ready`) in S3.
- **On heartbeat**: Auto-assign highest-priority ready task to idle bots (if Chief is unavailable).
- **On item completion**: Unblock dependent items in S3, echo to disk.

### Earned Value Management

| Metric | Formula | Meaning |
|---|---|---|
| PV (Planned Value) | Σ estimates for scheduled work | How much should be done |
| EV (Earned Value) | Σ estimates for completed work | How much is done |
| AC (Actual Cost) | Σ actual effort | How much was spent |
| SPI | EV / PV | Schedule performance (< 1.0 = behind) |
| CPI | EV / AC | Cost performance (< 1.0 = over budget) |
| EAC | Budget / CPI | Forecast total cost |

Use **0/100 completion** — items are 0% until done. No partial credit.

### Flow Metrics

| Metric | Measures |
|---|---|
| Cycle Time | Start to finish per task |
| Lead Time | Created to finished per task |
| Throughput | Completions per day |
| Velocity | Completed estimate hours per period (3-period rolling average) |
| Blocked Rate | Blocked / total items |

## Responsiveness

The Chief's Main Brain is **non-blocking**. It never performs heavy tasks. If only the Chief is available, it still branches to a Branch Brain to do the work, ensuring the Main Brain is always ready to field the next message from the Captain.

## Verification

1. **Chief elected** — Two bots in the same room, lowest rank number gets Chief.
   *Check:* Lower-ranked bot has ⭐ pip. Higher-ranked has 🟢.

2. **Chief responds to unaddressed messages** — Post a message without mentioning any bot.
   *Check:* Chief responds. Non-Chief bots stay silent.

3. **Chief delegates** — Chief receives a complex request.
   *Check:* Chief branches to thread, tags another bot for the work.

4. **Chief re-election** — Dismiss the current Chief.
   *Check:* Next-lowest-rank bot gets ⭐. Display name updates.

5. **Chief non-blocking** — Send rapid messages while Chief has an active thread.
   *Check:* Chief's Main Brain responds immediately on main timeline.
